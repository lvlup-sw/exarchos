## 1. Thesis

v2.11.0 is the "Verification & Reliability" milestone. Three of its loose ends close together as one preview:

1. **Reliability** — two latent correctness bugs that silently corrupt state (a delegation hazard, a recovery anti-pattern) ship as fast, independent fixes.
2. **Verification** — the risk-proportional ladder's *binding model* landed (#1546); its *measurement* loop (#1525) is the one acceptance gate still open on epic #1515. Closing it makes the token win **measured, not asserted**.
3. **Event-sourcing maturity** — the read/authority side is the documented gap (the leverage study). Four recommendations turn an already-correct intent into a *structurally-enforced* one: delete the legacy file path, collapse to one reducer, add a bounded-fold primitive, and wire upcasting — each making drift **unrepresentable**, not merely tested.

The unifying discipline (study §4): *the right place to enforce an invariant is the type system or a CI gate, not code review.* Every slice below either adds such a guard or removes the surface that needed one.

## 4. Wave 1 — Reliability bugs

### 4.1 #1542 — honest delegation readiness under native isolation

**Problem.** `prepare_delegation(nativeIsolation:true)` returns `ready:true` while its own payload reports `worktrees.ready:0` / `readyTaskIds:[]`. If the host no-ops worktree creation, agents land in the **shared main checkout** and dirty it; the only backstop is the implementer's own in-worktree `pwd | grep .worktrees` guard, which fires *after* corruption.

**Design decision — warn, don't block (INV-12 + INV-5b).** Under native isolation the orchestrator *cannot* know at prepare-time whether the host will materialize worktrees (creation happens at dispatch, downstream). Flipping `ready:false` would break the native-isolation contract (#1512: the host owns isolation). So readiness stays `true`, but the affordance stops lying: `prepare_delegation` appends a `warnings[]` entry when `nativeIsolation === true && worktrees.expected > 0 && worktrees.ready === 0` — *"native isolation requested; N worktrees expected but 0 confirmed ready — verify the host materializes worktrees or dispatch may land in the shared checkout."* The numbers are already computed; the `warnings[]` array already exists on the output schema (currently unused for this case). This is the INV-5b output-contract carrier doing its job.

**Design decision — verify-back belongs in the playbook (INV-11).** Code can't observe the host's spawn result; the delegate **skill** gains an orchestrator-side post-dispatch / pre-edit step on the native-isolation path: confirm each agent reports a `.worktrees/` cwd; if not, fall back to manual `git worktree add -b <branch> <path> <integration-tip>` and redirect the agent (exactly the observed recovery). This makes the task-isolated posture hold in practice, not just in prose.

**Touches.** `orchestrate/prepare-delegation.ts` (warning emission), the delegate skill source under `skills-src/` (verify-back step → regenerate `skills/**`, INV-4). **Effort:** S. **Risk:** low (additive warning; skill prose).

### 4.2 #1307 — merge recovery uses the native primitive (INV-14)

**Problem.** INV-14 requires reversal to prefer the operation's own recovery primitive (`git merge --abort`), then a refuse-to-discard substrate undo (`git reset --keep <sha>`), and **never** a destructive overwrite (`git reset --hard`). The catalog already cites `merge-orchestrate.ts` as INV-14-bearing, but the issue flags a residual `--hard` path; a first grep finds only a *comment* at `merge-orchestrate.ts:370` ("a rollback would `git reset --hard` to the wrong commit"). **Grounding is a planning task:** audit every rollback/recovery branch in `merge-orchestrate.ts` (and any executor it calls) for an actual `--hard`, an unguarded `reset`, or a path that *would* reach for `--hard`.

**Design decision.** Any reversal path resolves through the INV-14 ladder: in-merge → `git merge --abort`; post-merge rewind → `git reset --keep <sha>` (refuses to discard uncommitted work); never `--hard`. Indeterminate outcomes surface via the `recoveryError` discriminator (`'reset-keep-blocked' | 'reset-failed' | 'unexpected-mid-merge-drift'`) on the terminal result so callers see indeterminate states explicitly rather than as silent successes. If the audit finds the path already conforms, the deliverable shrinks to a regression test that *pins* the ladder (no `--hard` reachable) — which is worth landing regardless.

**Touches.** `orchestrate/merge-orchestrate.ts` (+ executor). **Effort:** S. **Risk:** low.

## 5. Wave 2 — Verification closeout (#1525, R10)

**Problem.** Epic #1515's acceptance bar is "demonstrated token reduction at equal-or-better correctness," explicitly gated on resolving the `subagent.tokens_used` telemetry gap. Confirmed: `subagent.tokens_used` is emitted *nowhere* in the codebase, so `team_performance` / `delegation_timeline` are empty and the token win is unmeasurable.

**Design — two INV-1 left-folds, no side tables.**
1. **Token telemetry.** Emit `subagent.tokens_used` at subagent-dispatch completion (the delegation/team telemetry path), carrying the per-subagent token counts. The existing `team_performance` / `delegation_timeline` view materializers fold it — populating what is currently empty. No new store; the event *is* the record (INV-1).
2. **Mutation-score trend.** Fold per-skill / per-module mutation score over the existing `gate.executed` events into the `code_quality` / `eval_results` views as a trend (INV-1 left-fold — *no side table*). Full mutation runs stay **offline/nightly, sampled** (wall-clock-dominated → never on the inner loop, INV-10 liveness for the runs themselves). The trend proves the lighter ladder did not erode assurance and can feed R1's tier classifier (weak modules ⇒ higher tier) later.

**Acceptance (this *is* #1515's gate).** Token telemetry populated for a representative batch; mutation-score trend queryable per skill via `exarchos_view`. **Invariant:** INV-1 (folds, not side tables), INV-10 (mutation-run liveness), INV-5b (view carrier). **Effort:** M. **Risk:** low-med (telemetry emission plumbing). On completion, #1515 is re-evaluated for closure (its remaining Phase-1/2/3 SIV subs are *out of scope* for this preview — see §8).

## 6. Wave 3 — Event-sourcing read-path hardening

The leverage study (§4, R1–R4) is the detailed design; this wave executes it. Summaries + the structural guard each adds:

### 6.1 #1555 (R3) — bounded-fold primitive *(build first)*
Extend `projections/rebuild.ts` with a cursor; add `projectAt(reducer, store, stream, {untilSequence?|untilTimestamp?})`, `diffStates(a,b)`, `bisect(reducer, store, stream, predicate)`. Warm-start from the latest snapshot whose `sequence <= N` (the `projection_snapshots` DESC index already supports the bounded read); purity guarantees `projectAt(N) ≡ fold(events[0..N])`. Read-only. Surfaced minimally as `exarchos_workflow({action:'get', asOf})` later; `diff`/`bisect` stay internal first. **Why first:** counterfactual replay de-risks #1554/#1556 and turns event-log slices into cheap golden fixtures. **Invariant:** INV-1, INV-10; **INV-15 guard** — stays a *local* bounded fold, never streaming to replicas.

### 6.2 #1556 (R4) — wire upcasting at the query choke point *(independent)*
Map every event through `migrateEvent` inside `store.ts:query` — the single seam every reader passes (rehydrate, reconcile, views, `resolveWorkflowState`). Identity no-op today (`eventMigrations:[]`, `EVENT_SCHEMA_VERSION:'1.0'`), load-bearing the moment a migration registers. **Structural guards:** (a) no-bypass CI gate — forbid constructing a `WorkflowEvent` from a raw backend row anywhere except the `query` choke point (sibling of the `Database`-import gate); (b) version-coverage build-time test — every `schemaVersion < EVENT_SCHEMA_VERSION` must have a migration path, or the build fails; (c) golden-log replay corpus (cheap once #1555 lands). Snapshots already invalidate on `schemaVersion` mismatch, so a bump forces a clean rebuild *through* the upcaster. Unblocks #1296. **Invariant:** INV-1 (log immutable; evolution is read-time).

### 6.3 #1504 (R1) — delete the legacy `.state.json` path
Per the maintainer steer in the study: `.state.json` is **legacy**, SQLite is the sole SoT. Remove the `stateFile` branch (and ultimately param) from `resolveWorkflowState`; stop *writing* the file (retiring its `_eventSequence` cursor + `_version` CAS); migrate the ~10 call sites still passing `stateFile` to the event-store-only form the already-safe callers use. **The one precondition (the real work):** a **field-coverage audit** — every datum currently *only* in the file must be event-sourced and folded by `workflowStateProjection`; that audit is the gate on deletion (and #1555's `diffStates` over real history proves projection equivalence). **Structural guard:** CI gate — no production code reads or writes `*.state.json`. Sequence after the `refactor-1486` gate-handler migration. **Invariant:** INV-1.

### 6.4 #1554 (R2) — one canonical `workflow-state@v1` reducer
Promote `workflowStateProjection` (most complete, already the materializer) to a single registered `workflow-state@v1` `ProjectionReducer` alongside `taskstore`/`merge-orchestrator`; every reader folds through it; bridge `ViewProjection ↔ ProjectionReducer`. Collapses three folds + the manual `INITIAL_PHASE` table (#1504 already removed fold #3). **Structural guards (strongest first):** (a) compile-time exhaustiveness — `switch (event.type)` with `default: assertNever(event.type)`, so an unhandled new event type is a *type error* (or must be in an explicit observability-only no-op set); (b) single-fold CI gate `scripts/check-single-workflow-fold.mjs` — any `switch (event.type)` over `WorkflowEvent` outside the canonical module fails the build; (c) registry singularity — extend the duplicate-`id` throw to reject a second reducer claiming the `workflow-state` domain. **Depends on #1504.** Golden replay equates pre/post projection over a representative log (cheap via #1555). **Invariant:** INV-1.
