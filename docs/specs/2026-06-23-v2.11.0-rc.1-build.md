# v2.11.0-rc.1 build

## Design & Rationale

### Problem Statement

v2.11's substantive content — the **Z1 adaptive-depth zone** (verification ladder #1515,
design+plan collapse #1581, ship-gate methodology #1592) — is fully shipped and merged to
`main`. That is what makes the current `2.11.0-preview.4` tag a *candidate*. But the milestone
still carries **12 open issues**, all already labeled `build:rc.1` (a clean 1:1 mapping — no
hidden epic children: #1510's references #1087/#1470/#1483/#1485/#1507/#1508 are all closed).

The decision (2026-06-23) is **complete all of them** — no deferral to GA or v2.12. The rc.1 cut
line is therefore "every `build:rc.1` issue closed + release gates green," not "the Z1 thesis is
true." This spec locks that scope, sequences the heterogeneous work into dependency-correct waves,
routes each issue to its execution path, and defines the rc-readiness gate.

**One scope addition.** #1402 (Windows ancestry-preflight phase-2 RCA) is externally blocked: its
phase-2 root-cause analysis cannot begin until a **Windows host** runs `merge_orchestrate` with
`EXARCHOS_PREFLIGHT_DEBUG=1` and produces the failing `merge.preflight` event carrying the 9-field
debug payload (phase-1 instrumentation already shipped via #1401). There is no Windows CI today.
The chosen unblock is to **pull #1170 (windows-latest CI matrix) forward** from v2.12 into rc.1 —
it both captures #1402's payload automatically and raises the Windows-regression floor permanently.
rc.1 scope is thus **13 issues: the 12 milestone issues + #1170**.

### Constraints (load-bearing invariants — re-assert at the rc gate, don't rediscover at GA)

A release-candidate cut must *prove* these haven't regressed across the preview.4 → rc.1 boundary:

- **INV-2 (facade-equivalence)** — CLI⇄MCP parity. #1165/#1319 add surfaces that must exist on
  *both* facades, not one. The rc gate asserts parity.
- **INV-6 (workload-agnosticism)** — the shipped Z1 gates must stay workload-agnostic. This was the
  exact v2.10 GA-blocker class (#1470); re-assert it now rather than at GA.
- **INV-15 (single-machine-frame)** — #1592 shipped the ship-gate as a no-daemon pre-push hook; no
  new long-running daemon may enter via #1319/#1300/#1510.
- **INV-5b (output-contract)** — the ToolResult carrier shape is consumer-pinned; #1319's `feedback`
  action and #1242's new event must not mutate it.
- **INV-12 (next-actions-as-affordance)** — #1300/#1510 reshape workflow affordances; `next_actions`
  must still publish correct runtime affordances.

### Requirements (DR-N)

- **DR-1 — Scope is exactly the 13 `build:rc.1` issues.** rc.1 ships when all 13 are CLOSED and no
  `build:rc.1`-labeled issue remains open. No silent deferral; any descope is an explicit label/
  milestone move recorded on #1599. *Acceptance:* `gh issue list --label build:rc.1 --state open`
  returns empty **and** every closed `build:rc.1` issue resolves to a merged PR on `main`.
  **PR strategy (decided 2026-06-23): a SINGLE rc.1 integration PR** from `feat/v2.11.0-rc.1-build`
  closing all 13 issues (`Closes #…` repeated per issue — comma-lists only close the first). DR-1's
  per-issue-PR check therefore relaxes to "each issue's closing commit is present in the merged rc.1
  PR"; the cut script verifies each issue is referenced by that merged PR, not 13 separate PRs.

- **DR-2 — #1170 lands first as #1402's enabler.** windows-latest is added to the CI matrix and a
  green run captures the `merge.preflight` debug payload (or a documented negative result) before
  #1402's phase-2 RCA is attempted. *Acceptance:* a windows-latest job exists in CI and #1402's RCA
  cites a real (or explicitly-null) Windows debug payload.

- **DR-3 — Shepherd-skill edits are sequenced, not parallel.** #1505 (conformance pointer) and #1300
  (self-healing markdown fixes) both edit `skills-src/shepherd/SKILL.md`; they land in series with a
  rebuild (`npm run build:skills`) between them to avoid the R3 edit-collision class (#1599 ledger).
  *Acceptance:* the two are not dispatched in the same wave; `skills:guard` is green after each. Note:
  `skills:guard` runs `lint:inv6 || true` (advisory — swallows failures), so INV-6 conformance of the
  shepherd edits is a **manual** sign-off under DR-6(e), not caught mechanically by `skills:guard`.

- **DR-4 — Each issue closes via its declared route with its own acceptance criteria.** Small fixes
  (#1352/#1337/#1505) via oneshot; ready features/guards (#1317/#1321/#1242/#1319/#1165/#1300) via
  plan; the spike #1475 via discover (evidence + decision, not a forced redesign); the epic #1510
  via its own plan cycle against the locked design `docs/designs/2026-05-31-onboard-doctor-consolidation.md`.
  *Acceptance:* every closing PR references its issue and satisfies that issue's stated acceptance.

- **DR-5 — SDK-lowering note on HSM/gate-touching items.** Any rc.1 change that edits
  `hsm-definitions.ts` / `playbooks.ts` / gate chains (candidate: #1300, #1510, #1242) carries an
  explicit SDK-combinator mapping per #1599 coordination rule 3, so #1253 (P7 migration) consumes it
  unchanged. *Acceptance:* such PRs include the lowering note; non-HSM items are exempt.

- **DR-6 — rc-readiness gate: three tiers, honestly labeled.** The cut runs only after all three:
  - **Tier 1 — CI-enforced, fail-closed (standing status checks, cannot be skipped):** (a) DR-1
    passes (empty label list **+** merged-PR-per-issue); (b) `main` CI is green **including the
    windows-latest job wired into the `ci-gate` aggregator's `needs[]`** — adding a `test-windows` job
    to `ci.yml` without adding it to `ci-gate.needs` is itself a DR-6 violation (the new job must be a
    required status check, not an orphan); (c) the **INV-2 parity suite**
    (`servers/exarchos-mcp/src/**/parity.test.ts` — a real, CI-run assertion of CLI⇄MCP equivalence,
    already in `test-mcp`) is green.
  - **Tier 2 — cut-checklist mechanical command (run once at cut; NOT a standing CI gate — no new
    script):** (d) the release owner runs a grep over the rc.1 diff for **new daemon /
    long-running-listener** constructs — e.g.
    `git diff <preview.4-base>..rc-tip -- 'servers/**/*.ts' 'src/**/*.ts' | grep -nE '^\+.*(setInterval|\.listen\(|while *\(true\)|for *\(;;\))'` —
    and confirms zero new matches (INV-15). This is a concrete, repeatable command, but it is a
    one-time cut check, not a CI status check; the spec does **not** claim a standing INV-15 gate
    exists (it does not).
  - **Tier 3 — human sign-off (explicitly NOT mechanical, recorded on the cut checklist):** (e) INV-6
    (workload-agnosticism) and the INV-12/INV-5b carrier-shape review are a **named reviewer
    judgment** — `lint-inv6` is advisory (exits 0 always) and the INV-6/INV-12 audit-mode prose is not
    a script, so this leg is a checklist sign-off, not a gate.
  - Then (f) `/exarchos:release` bumps `2.11.0-preview.4 → 2.11.0-rc.1`, syncs, validates, tags, and
    triggers the Release workflow. *Acceptance:* the `v2.11.0-rc.1` tag exists only when Tier-1 (a)–(c)
    are CI-green, Tier-2 (d) is run with zero matches, and Tier-3 (e) is signed off on the checklist.

- **DR-7 — Error handling / partial-failure isolation.** A failing gate on any single issue blocks
  **only the rc cut**, never the other waves — waves are independent work, not a transaction. #1402
  carries an explicit fallback with a **defined non-reproduction rule**: "cannot reproduce" =
  **3 consecutive green windows-latest runs** of the `merge_orchestrate` ancestry path with
  `EXARCHOS_PREFLIGHT_DEBUG=1` and zero `ancestry.passed:false` events. A **flaky** result (repros
  intermittently) counts as *reproduced* — it does NOT qualify for non-repro close. On confirmed
  non-repro, the **release owner** (the maintainer cutting rc.1) records the disposition —
  close-as-not-reproducible (with the 3-run evidence linked) or keep-open-with-evidence (bumped to
  v2.12) — within the rc-cut checklist; #1402 is the **only** issue permitted a non-merge close, and
  only via this rule. *Acceptance:* a non-reproducing #1402 has the 3-run evidence + an owner-signed
  disposition before the cut; no wave is held hostage to another wave's red gate.

- **DR-8 — Shared-file edges are declared and merge-serialized.** Tasks that edit the same file are
  **not** parallel-safe even across waves unless the earlier wave is **merged to the integration tip
  first**. The known shared-file edges: `event-store/schemas.ts` (T6 #1319 + T7 #1242),
  `registry.ts` / `adapters/cli.ts` (T6 #1319 + T11 #1510 + the CI guards' action registration), and
  `skills-src/shepherd/SKILL.md` (T3 #1505 + T8 #1300, already in DR-3). For the registry edges, a
  **registration-schema collision check** runs after each colliding task merges — two actions sharing
  a field name with different base types make `buildRegistrationSchema` THROW at startup
  (project-known failure class), so the integration suite must boot the MCP server after each merge.
  *Acceptance:* the Parallelization summary lists every shared-file edge; colliding tasks are merged
  in declared order, not dispatched concurrently; MCP server boots clean after each registry merge.

### Chosen Approach

Drive the 13 issues as **one coordinated rc.1 batch**, dependency-ordered into four waves plus the
release cut. The batch is a *coordination* layer over the existing per-issue tracking — each issue
already carries its own scope/acceptance in its body, so this spec sequences and gates rather than
re-designing. Heavy items (#1510 epic, #1319, #1300) flow through their own `/plan` cycles; the
`/plan` decomposition of *this* spec is the wave-ordered task list of "drive issue #X to closed."

**Waves (dependency-correct):**

| Wave | Issues | Why this order |
|---|---|---|
| **W0 — enabler** | #1170 | windows-latest CI must exist before #1402 can capture its payload (DR-2) |
| **W1 — ready small fixes** | #1352, #1337, #1505 | scoped, low-blast, parallelizable; #1505 is the *first* shepherd edit (DR-3) |
| **W2 — CI guards + high-pri feature** | #1317, #1321, #1319 | independent additive surfaces; #1319 is priority:high |
| **W3 — workflow/provider features** | #1242, #1165, #1300 | #1300 is the *second* shepherd edit — lands after #1505 + rebuild (DR-3) |
| **W4 — spike + epic** | #1475 (discover), #1510 (plan) | heaviest; #1510 against its locked design; #1475 yields evidence |
| **W5 — gated** | #1402 | runs after W0 produces (or fails to produce) the Windows payload (DR-7) |
| **Cut** | — | rc-readiness gate (DR-6) → `v2.11.0-rc.1` |

### Alternatives considered

- **Cut rc.1 now, defer the residue (original proposal).** Rejected by the maintainer: "complete
  all of them." The Z1-thesis-is-enough framing is sound for *naming* a candidate but the team wants
  the milestone fully drained before the rc label.
- **#1402 manual Windows trigger / lone deferral.** Both viable; rejected in favor of pulling #1170
  forward (chosen 2026-06-23) because it unblocks #1402 *and* permanently closes the Windows-CI gap
  rather than leaving a one-off manual capture or a single open exception.
- **One mega `/plan` decomposition of all 13 as flat tasks.** Rejected — it loses per-issue design
  fidelity for the epic (#1510) and the priority:high feature (#1319), which deserve their own
  plan cycles. This spec stays a coordination layer that *routes* to those cycles.

**Sequential / merge-serialized edges (the complete set — DR-8):**
- **T0 → T12** — #1402 RCA needs the Windows debug payload that T0's CI run captures.
- **T3 → T8** — both edit `skills-src/shepherd/SKILL.md`; rebuild between (DR-3).

  check after each (registration-schema field-collision throws at startup — DR-8).

**Everything else is parallel-safe** in worktrees within its wave. The "parallel-safe" claim holds
**only** under wave-merge discipline: each wave's PRs merge to the integration tip before the next
wave's colliding task is dispatched — concurrent dispatch on a shared file is a DR-8 violation.
