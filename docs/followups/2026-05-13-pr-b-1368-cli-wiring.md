## Why

Wave 0 (#1369) shipped `toCliResult(env, format)` in `cli-format.ts` and `EXARCHOS_CLI_ENVELOPE=0` opt-out, but **the CLI entry path still routes through the legacy `emitResult` function** in `adapters/cli.ts`. That function writes raw `JSON.stringify(result)` under `--json` — the pre-carrier-swap shape, not the new envelope.

The fix is a one-liner:

```ts
function emitResult(result: ToolResult, json: boolean, format?: 'table' | 'json' | 'tree'): void {
  if (json || format === 'json') {
    toCliResult(toEnvelope(result), 'json');
    return;
  }
  prettyPrint(result, format);
}
```

The reason it didn't ship in Wave 0 is that **61 in-tree parity tests** across `parity/`, `__tests__/parity/`, and per-module `*.parity.test.ts` files assert byte-equal raw-`ToolResult` JSON between CLI `--json` output and MCP. With the envelope wrapping, the shape becomes `{success, data, next_actions, _meta, _perf, ...}` instead of bare `{success, data, ...}` — every parity test fails until updated. Wave 0 chose to ship the structural surface (`toCliResult` + opt-out flag) and defer wiring + test migration to this PR.

The completed wiring delivers INV-2 (facade equivalence) — CLI `--json` stdout and MCP `structuredContent` carry the same envelope byte-for-byte modulo timestamps.

## Risks

- **Test coverage drift** — masking `_meta` fields could accidentally hide a real assertion. Mitigation: per-file diff review during Phase 2; each subagent reports which fields it masked and why.
- **Compact vs pretty JSON** — `toCliResult` uses `JSON.stringify(env, null, 2)` (pretty); the existing `--json` emitted single-line. Tests that did `stdout.includes('\n')` to detect multi-output may misbehave. Mitigation: scan for line-count assertions before Phase 1 wiring.
- **External CLI consumers** — same risk Wave 0's #1368 deferral existed for. Mitigated by the EXARCHOS_CLI_ENVELOPE=0 opt-out shipped in Wave 0; PR-B does not re-introduce it.
