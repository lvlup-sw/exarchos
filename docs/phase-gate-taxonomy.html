The phase-gate taxonomy

What a gate is in Exarchos, where it is declared, how it is selected, how it runs, what it does to the world, and what it leaves behind. Six axes, measured from the live source rather than from prose — because the interesting failures are all places where two of the six disagree.

01 The spine

A gate is never bound to a phase. It is bound to a phase kind.

This indirection is the load-bearing design decision, and it is deliberate (INV-6, workload-agnosticism): an obligation attaches to the kind, so it composes across every workflow type — present and future — without new playbook code. KIND_OBLIGATIONS in workflow/phase-kind.ts is the single grant point, keyed only by kind, never by workflow name, phase id, or transition.

The four gate-bearing kinds each dispatch to exactly one resolver, and each resolver emits a family in its own vocabulary — the bottom line of each box. Only plan and ladder name registry actions.

The four families, and the four vocabularies they speak

ResolvedGate is a discriminated union tagged by family. The tag exists precisely because the four are heterogeneous — and the heterogeneity runs deeper than the type: only two of the four families name things that are actually registry actions.

◆Why this matters

A consumer asking “which gates ran for this phase?” gets four answer shapes from one union. Two families resolve to things you can dispatch and query by name; one resolves to a folder name whose verdict is a state field; one resolves to labels that exist only inside a single handler. Any cross-family report, coverage metric, or admission predicate has to special-case all four.

02 Selection

Each family varies along its own axis — and each axis is a pure frozen table.

All four policy modules share one discipline: a const table, no config reads, no I/O, strict-superset rungs, and an override layer that composes on top rather than replacing. The gate set is resolved once at phase entry and frozen into the durable log (phase.entered.resolvedGates), so what was owed stays auditable after the fact instead of being re-derived.

plan-structure · axis = designDepth

  • thin (2) — decomposition, coverage
  • standard (5) — + spec-coverage, provenance, traceability
  • deep (6) — + exploration-depth

The standard rung is pinned equal to the registry's static PLAN_PHASES binding, so graduating the resolver to read depth was provably behavior-neutral at the default.

review-contract · axis = workflowType × riskTier

  • low / medium (1) — review
  • high (2) — + mutation-adequacy

The workflow tier is max-of-tiers across the wave's tasks, so one high-risk task pulls the mutation backstop onto the whole review boundary.

synthesis-readiness · no axis

  • fixed 5 legs — task-completion → tests → typecheck → document → stack

Membership here is the obligation order; evaluation and config-resolved severity are owned entirely by prepare_synthesis.

fail-closed on a bad axis value

  • An out-of-table designDepth throws, and the throw is converted to phase.blocked — never a silent open transition.
  • An unresolved riskTier is carried as 'unknown' rather than collapsed, because the ladder and the review roster have opposite fail-safe directions.

03 Encoding

Four independent declaration surfaces, only partly overlapping.

“Is this a gate?” has four answers depending on which surface you ask, and the four populations are not the same set.

Surface 1 — registry action metadata

gate: { blocking, dimension, gateClass } on a BuiltinToolAction.

  • 28 actions carry it — 14 blocking, 14 advisory
  • 18 name a convergence dimension (D1–D5, plus one mutation-adequacy)
  • 9 name a gateClass; 8 are longRunning; 1 is deprecated

Surface 2 — the provider registry

9 SupportedGateClass members = 5 mechanical + 4 phase.

  • Exactly one provider per class, enforced by satisfies Record<…> — a new class is a compile error until it gets an owner
  • Duplicate and missing providers are typed diagnostics, not runtime surprises
  • The action identity is the proof-domain providerRef; no second namespace

Surface 3 — runbook chains

Ordered steps with onFail: 'stop' | 'continue'.

  • 5 of 18 runbooks carry a gate step
  • 12 gate steps halt the chain; 3 continue
  • The plan-phase runbooks carry no gate steps — they are decision runbooks

Surface 4 — runtime severity & mode

Two orthogonal axes resolved per call, both workflow-keyed.

  • Severity — 5-level precedence: gate override → dimension disable → per-workflow ladder default → dimension severity → blocking
  • Mode — audit vs enforce, IMPLEMENT-only; oneshot is the sole audit workflow

▲The registry flag is a mirror, not the truth

gate.blocking in the registry mirrors the runtime default so drift checks can read it statically — but the value that actually governs a run comes out of resolveGateSeverity with project config layered in. check_mock_boundary and mutation-adequacy are declared blocking: false for exactly this reason: the demotion lives in DEFAULTS.review.gates, and a project override can raise either back to blocking without the declaration changing.

04 Execution

Three tracks. Only one of them produces a proof.

A migration is half-finished here, and the seam is visible in the code as an explicit opt-out flag. The durable runner is the intended destination: it is the single authoritative producer of the gate signal for every class it owns, minting gate.executed from the same persisted evidence record it just wrote — so the signal and its proof cannot disagree.

Steps 9 and 10 are the coupling that makes the ladder family trustworthy: the signal is minted from the same persisted record as the proof, so the two cannot disagree. Nothing returns to the caller before the durable append.

◆The migration seam, stated in the code

GateRunnerDependencies.emitGateExecuted defaults to true and exists solely as a per-class opt-out for legacy providers that still emit their own row from inside the provider body — plan-coverage, provenance-chain, review-verdict and prepare-synthesis. The flag's own docstring says to delete the provider's emitGateEvent call rather than the default when each is migrated. Ownership stays exactly one producer per class throughout.

05 Effects

Two effect vocabularies, deliberately kept apart — and a third question neither answers.

Gates are the most effectful things in the system: they spawn compilers, run whole test suites, and in one case revert the working tree and put it back. Two separate models describe that, and the code is explicit that folding them together would break both.

Model A — the effect ledger (static census)

architecture/effect-ledger.ts · 3 primitives: filesystem, process, network.

  • A detection vocabulary — its members are exactly what a static scan of import specifiers can find
  • Closed-world: any unvetted bare package counts as network, so a client cannot hide behind a novel name
  • 38 ownership rules map every occurrence to a typed owner + idempotency + compensation contract
  • Unowned occurrence → INDETERMINATE_OWNER; a rule with no live occurrence → STALE_OWNERSHIP. Both fail the census.

Model B — the effect carrier (runtime value)

dispatch/core/effect-carrier.ts · 6 classes: filesystem, process, vcs, install, network, compensation.

  • A discriminated union with a first-class dry-run arm that is structurally incapable of running the effect
  • EffectPlan.emits is typed as EventType — an unregistered event name is a compile error
  • Emission resolves against neither class nor owner: the event catalog is its only authority
  • The header states outright that the two EffectClass types must stay distinct, and the layer table forbids the import edge that would merge them

▲Every gate's process effect funnels through one module

verbs/gates/gate-utils.ts is the sole child_process importer among the gate modules, and 23 modules import it. Every lint run, every test suite, every git call the whole gate surface makes therefore attributes to that one file — and the per-module rule means the ledger cannot say which gate spawned what. The 25 “no detected effect” modules above include static-analysis.ts and test-adequacy.ts, two of the most effectful things in the system.

Ownership compounds it: the rules covering gates are declared at layer granularity — process: verbs/ → orchestrate-process-owner and filesystem: verbs/ → orchestrate-fs — and the process rule's idempotency contract reads “per-call: orchestrate probes/gates own their re-run semantics.” The ledger satisfies its one-typed-owner mandate by delegating the answer back to the gates.

◆The one gate that mutates the tree

check_test_adequacy is mutation-testing at N=1: it reverts the task's source hunks, keeps the tests, re-runs them, and asserts at least one goes red — proving the tests are not vacuous. It restores the working tree unconditionally (INV-14). That is a compensation contract in the effect-carrier sense, implemented inside the gate; the ledger records it only as an anonymous verbs/ filesystem occurrence.

06 Enforcement

Four places a gate can actually stop something — and a fifth that is declared but dormant.

Edge 1 — runbook chain ordering

onFail: 'stop' halts the chain; 12 of 15 gate steps do. This is what makes the per-task ladder binding: task_complete is the terminal step, so no blocking gate may follow it.

Edge 2 — the task_complete admission

Reads gate.executed rows off the stream and refuses with GATE_NOT_PASSED. It enforces exactly one universal gate: static-analysis. The tier-scaled gates are deliberately not hard requirements here, because at this point the tier is unknown.

Edge 3 — the phase boundary

Resolve-then-freeze on phase.entered; a resolver fault becomes phase.blocked (fail-closed, never a silent open). phase.exited carries allRequiredGatesPassed as a required boolean — a missing value is rejected at the emission boundary rather than persisted as false.

Edge 4 — config severity and mode

withConfigSeverity turns a failure into a warning, or skips the gate entirely, per project config. The audit mode axis does the same at kind granularity for IMPLEMENT phases in oneshot workflows.

The fifth edge: an admission-control architecture that is declared but not enforcing

Alongside the live signal path sits a full evidence-backed admission engine — requirement resolution, evidence selection, policy evaluation, waivers, contradictions, reassessment, remediation. Its event vocabulary is registered in the catalog. Most of it has never been emitted.

▲The cutover gate gates itself

Flipping enforcement from the legacy HSM guard path to the admission engine is itself event-sourced: it requires a recorded admission.rollout-decision followed by an admission.enforcement-enabled fact, and the module structurally refuses to build that fact for an unsatisfied gate. Six independent conditions must hold — a clean deterministic corpus, at least 20 comparable live attempts, every phase kind observed, both allow and deny outcomes present, a comparable disagreement class on every attempt, and a healthy observer.

The last two exist because of an audited defect the module names in its own header: “20 attempts that all threw would satisfy three of four conditions.” The observer-health condition is the direct answer to the vacuity question — a dead observer's empty evidence stream must never read as a clean one. The gate is RESERVED and deliberately not yet consulted by a production caller.

07 Findings

Where two of the six axes disagree.

Each of these is a measured disagreement between declaration surfaces, not a style objection. The pill marks whether it is a structural observation or a live gap.

  1. Two blocking gates leave no record at allgap

    validate_pr_stack (synthesize) and debug_review_gate (debug-review) are declared blocking: true and emit nothing. Three more advisory gates — check_coverage_thresholds, spec_coverage_check, prepare_review — are the same. Their verdicts exist only in the tool response, so no projection, no admission predicate and no audit can establish that they ran, let alone passed.

    registry/actions/orchestrate/{verification,review-ops}.ts · verbs/gates/spec-coverage-check.ts · verbs/vcs/validate-pr-stack.ts

  2. A resolved plan obligation that is not a gate in the registrygap

    generate_traceability is a member of the plan-structure sequence at the standard and deep rungs, so the resolver hands it to the phase as an obligation — but it carries no gate metadata and emits nothing. It is a gate to one authority and not a gate to the other.

    workflow/plan-depth-policy.ts PLAN_DEPTH_GATE_NAMES vs the registry action declaration

  3. The four families speak four vocabulariesstructural

    ladder and plan resolve to registry action names; review resolves to skill folder names under content/; synthesis resolves to leg labels that exist only inside prepare_synthesis. The family discriminant makes this exhaustively checkable at the type level, which is the right containment — but any consumer that wants one answer to “which gates ran” must implement four.

    workflow/phase-kind.ts ResolvedGate

  4. 8 of 18 resolved obligations leave no record of their owngap

    The ladder family is fully coupled — 5 of 5 persist a content-addressed evidence artifact and mint the signal from it. The other three are not: 2 plan members are silent, the review dimension's verdict is a state field, and all 5 synthesis legs fold into a single aggregate row. Per-leg discharge is not reconstructable from the log.

    measured across registry autoEmits + provider emission sites

  5. The effect ledger cannot name which gate spawns a processstructural

    All gate process effects route through verbs/gates/gate-utils.ts — the only child_process importer among 40 gate modules, imported by 23 of them. Per-module attribution is a documented, deliberate boundary, but the consequence is that the ledger's answer for the entire gate surface is one file and one layer-granular owner whose idempotency contract delegates the question back to the gates.

    architecture/effect-ledger.ts EFFECT_OWNERSHIP · verbs/gates/gate-utils.ts:6

  6. Three live HSM phases are absent from ALL_PHASEScheck

    overhaul-plan-review (refactor, kind PLAN), plus gathering and synthesizing (discovery, kind GATHER). The two GATHER phases carry no obligation, so the practical effect is limited — but overhaul-plan-review is a PLAN-kind phase, so KIND_OBLIGATIONS grants it the full plan-structure gate set while the registry's PLAN_PHASES binding (plan, plan-review, overhaul-plan) does not list it. phases is a descriptive projection rather than a hard dispatch admission, so this surfaces as a describe / contract inconsistency rather than a runtime refusal — worth confirming that reading before acting on it.

    registry/phases.ts ALL_PHASES (26 entries) vs 29 live atomic HSM states

  7. One universal hard gatestructural

    task_complete enforces static-analysis and nothing else. Every tier-scaled gate is enforced only by runbook chain ordering. That is a defensible design — the tier is genuinely unknown at that point — but it means the strength of per-task verification rests on chain sequencing rather than on an admission predicate over the log.

    verbs/tasks/tools.ts:361

  8. Half the admission vocabulary has never been emittedstructural

    6 of 12 admission.* types are planned, including every member of the decision path (requirement-resolved, transition-decided, waiver-recorded, contradiction-recorded, and both reassessment types). The live half is the shadow apparatus. promotion.executed sits in the same planned bucket — the open row on epic #1822.

08 The optimal state

Exarchos has independently built three of the four roles in the standard policy architecture. The missing one is the decision.

Read against the industry frame, the phase-gate system is not idiosyncratic — it is a policy architecture with the decision point left implicit. Every gate action is simultaneously its own policy, its own decision function, and its own enforcement point. The four disagreements in §7 are all downstream of that single collapse. Naming the decision separates them.

The role names are the OASIS XACML vocabulary (PAP / PIP / PDP / PEP), which Kubernetes admission control, OPA Gatekeeper and Cedar all instantiate. The point of borrowing it is not conformance — it is that the vocabulary already has a word for each thing Exarchos currently leaves unnamed.

Role mapping: what already exists, and what is missing

RoleIndustry instanceExarchos todayGap
PAP — administration Gatekeeper ConstraintTemplate; K8s ValidatingAdmissionPolicy 4 pure policy tables + invariants catalog + .exarchos.yml present — but no declared combining algorithm across the four
PIP — information K8s paramKind / paramRef resource riskTier, boundaryTouching, designDepth, workflowType present — already frozen into phase.entered, which is the strong half
PDP — decision OPA/Rego; VAP CEL engine; Cedar absent — each gate decides for itself No shared verdict type; no Indeterminate; no separation of ran and said no from could not run
PEP — enforcement admission webhook, gator, audit controller 4 edges, none named No enforcement-point vocabulary, so per-point actions cannot be declared
Evidence in-toto Statement + SLSA Verification Summary Attestation content-addressed artifact + immutable subject + policyId/policyDigest closest to SoTA — already attestation-shaped for 5 of 28 gates

◆The evidence layer is the part to be proud of

The durable runner's design is an independent re-derivation of the in-toto attestation shape. in-toto's Statement binds a predicate to a subject whose elements MUST carry a digest and are assumed immutable; Exarchos's selectSubject picks a task, a commit SHA, or a content-addressed artifact digest — explicitly refusing to let mutable workflow state stand in for a commit. SLSA's Verification Summary Attestation records policy: {uri, digest} alongside the result; the gate runner already carries policyId + policyDigest. The remaining distance to a portable, verifiable attestation is small, and it is worth closing because it is what makes a gate result meaningful outside the Exarchos process — to Basileus, to CI, to an auditor.

▲What the frame does not license

INV-15 fixes Exarchos as a single-machine process manager with cooperative agents — concurrent, not distributed. So: no policy server, no network PDP, no Rego or CEL interpreter, no sidecar. The PDP here is a pure in-process function. That is not a compromise; it is the same conclusion Kubernetes reached in KEP-3488, which moved policy in-process precisely because “it is far safer to use in a fail-closed mode because it removes the network as a possible failure domain.” Exarchos never had the network in that domain to begin with, so it gets fail-closed for free — and already relies on it (phase.blocked on resolver fault).

09 The refactors

Eight, ordered so each one unblocks the next.

R1–R3 are the load-bearing set: they close every finding in §7 and are prerequisites for the planned taxonomy-v2 work. R4–R6 are the architecture. R7–R8 are debts against invariants Exarchos already declares. Nothing here requires the v3.0 SDK.

#RefactorClosesGroundingDepends on
R1 Split “said no” from “could not run”. Two declared axes per gate: failurePolicy: Fail | Ignore for errors and unresolvable preconditions, actions: [Deny | Warn | Audit] for a genuine false verdict. Findings 1, 7 K8s VAP keeps these strictly orthogonal: failurePolicy governs parse/type/runtime errors and misconfiguration; validationActions governs a validation returning false. —
R2 Make Indeterminate a first-class verdict. Four values, not a boolean: Permit, Deny, NotApplicable, Indeterminate. A skip-by-policy is NotApplicable; an unrunnable probe is Indeterminate and must never read as pass. The vacuity class outright XACML: “Indeterminate is not Deny, but must not grant access.” The PEP must define its handling of every outcome, timeouts included. R1
R3 Recording becomes unconditional. Every resolved obligation emits one result record whatever its severity. Severity stays configurable; whether a verdict is written down stops being configurable. Findings 1, 2, 4 K8s records audit annotations regardless of whether the binding includes Audit. Gatekeeper surfaces dry-run violations in the constraint's own status. The K8s Policy WG PolicyReport CRD exists so any decision point emits one shape. R2
R4 Name the four enforcement points and scope actions per point. runbook.chain, task.complete, phase.boundary, config.severity — one policy, a declared action at each point. Finding 7; informs #1773 Gatekeeper enforcementAction: scoped + scopedEnforcementActions, with named points (validation.gatekeeper.sh, audit.gatekeeper.sh, gator.gatekeeper.sh). Deny at one point, warn at another, by declaration. R1
R5 One obligation identity across all four families. Two things already true in-house

R2 is what makes the cutover gate honest

The six-condition cutover gate already carries a live-disagreement-class condition that discards attempts whose adjudication threw, and a live-observer-health condition so a dead observer cannot present as clean. Both are Indeterminate handling, hand-built for one call site. R2 makes it the type everywhere.

The reliability critique is already written

Taxonomy v2's problem statement says the registry “records authorship, not reliability” — source: auto|model says who composes the payload, not what the emission is welded to. The gate surface is the sharpest instance: gate.executed is auto for all 17 self-emitters, and that says nothing about whether a proof backs it.

▲One ordering constraint worth respecting

Taxonomy v2 sequences a Wave 0 ahead of everything because INV-9 is violated today: makeArtifactGuard accepts any non-null value ({"artifacts":{"plan":true}} clears a phase gate), and task_complete's only path through is an agent-supplied evidenceBypass. Its own words: “a correct taxonomy feeding a bypassable guard changes nothing.” The same applies here — R1–R3 give the PEP a verdict worth enforcing, but if the enforcement point can be waved through with a truthy literal, the refactor buys nothing. Close the bypass first.

§1–§7 are measured. §8–§9 are a proposal, and the sequencing assumes the taxonomy-v2 spec still reflects current intent.

11 What should survive

The dimension model is dead, and a third of the population is unreachable.

§8–§10 are mechanism refactors: applied literally, they preserve all 28 gates and improve how each is declared, decided and recorded. That is the wrong first move, because a measurable fraction of the population should not be instrumented at all — it should be deleted. This section is the population question, and it reorders the refactors.

▲The D1–D5 convergence model cannot pass, on any path

check_convergence requires ALL_DIMENSIONS.every(d => gateCount > 0 && converged). Four measured facts make that unsatisfiable:

1. The convergence view attributes a result by reading data.details.dimension, and gate-runner.ts contains zero occurrences of dimension. All five durable-runner gates are therefore invisible to it — including check_static_analysis and check_integration_suite, the only two D2 gates. D2 can never converge.
2. D3, D4 and D5 have two gates each, and not one appears in any runbook chain or any resolver sequence.
3. 10 of 28 gates carry no dimension at all, so the view cannot see them either.
4. D1 carries 9 gates under the label “Design Completeness” — including security scan, test adequacy, contract drift and mock boundary. It has become a catch-all.

No gate the system runs can populate D2, so convergence cannot pass on any automated path: the gate returns passed: false with uncheckedDimensions populated — and quality-evaluation invokes it with onFail: 'continue', which discards that. (An operator can hand-append a dimension-carrying gate.executed row, since the schema is not .strict() and the reader is tolerant. That is the only way it goes green, and it is not a path the system drives.)

▲But the dimension field itself is NOT dead — it has a second, live consumer

gate.dimension is also the key for resolveGateSeverity, which reads review.dimensions.D1…D5 from .exarchos.yml to disable a dimension outright or downgrade it to a warning. That is a documented, user-facing knob (yaml-schema.ts exposes DimensionKey as an enum). Deleting the dimension field would break it.

So the precise disposition is narrower than “delete the axis”: retire the convergence consumer, keep dimension as a severity-grouping key. What remains wrong there is naming and coherence, not existence — D1 groups 9 unrelated gates under the label “Design Completeness”. Whether severity should group by dimension at all, or by resolver family instead, is a design decision rather than a triage item, and it is a config-breaking change either way.

The root cause of the dead half is that two partitions of the same population compete. The resolver families (ladder / plan / review / synthesis) partition obligations by who resolves them and when — wired, frozen into phase.entered, load-bearing. The D1–D5 dimensions partition the same set by a quality taxonomy that only the severity overlay still reads, and that the convergence view reads incorrectly.

▲This reorders §9

R3 said recording becomes unconditional. Applied before triage it would pay to instrument gates that should not exist — and would turn check_convergence's permanently-false verdict into a permanent row in the log, which is worse than the silence it replaces. Triage first, then R3 over the survivors. R5 gets cheaper the same way: extending one obligation identity across the population is easier at 20 than at 28, and easier still once the competing dimension axis is gone.

The reachability, silence, duplication and dimension facts here are measured. The dispositions are a recommendation — and “resolve intent” marks the two cases where the measurement says nothing reaches this but only an owner can say whether that is neglect or obsolescence.
