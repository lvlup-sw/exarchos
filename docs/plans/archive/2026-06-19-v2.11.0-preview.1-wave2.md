## Grounded preconditions (verified this session)

- **Token atom exists:** `turn.completed` = `{turnId, outputTokens}` (`event-store/schemas.ts:985`), `auto`-emitted. **No teammate/session link in its data.**
- **Teammate identity exists, separately:** `team.task.assigned/completed/failed` + `team.teammate.dispatched` carry `teammateName`+`taskId` (`model`-emitted, feature stream).
- **Session→token link exists:** `session-provenance-projection` links `sessionId → {in,out,cacheR,cacheW}` and `sessionId → workflowId`.
- **The gap:** there is **no `turn→teammate` (nor `session→teammate`) correlation today.** Subagents run in their own sessions; their `turn.completed` atoms are not currently joinable to a `teammateName`. Every event *does* carry envelope correlation (`operationId`/`causationId`/`correlationId`, #1291) — the question is whether a subagent's turns are stamped with the dispatching operation's id.
- **Views to extend:** `views/team-performance-view.ts` (folds `team.task.*`, `team.spawned/disbanded`, `workflow.fix-cycle`; **no token fields**), `views/delegation-timeline-view.ts` (per-task durations).
- **Mutation atom (Half 2):** `gate.executed` (`auto`) + `mutation.executed` (`auto`, INV-10 liveness) already exist; `code-quality` / `eval-results` views are the fold targets.

### W2-1 FINDING (2026-06-19) — **A-pure is infeasible; the plan/research premise is false**

Traced the token + correlation path end-to-end in the running system. The premise that the
per-turn token atom is *"already emitted"* (research §TL;DR / §2 table) is **factually wrong**.

1. **`turn.completed` has NO producer.** Repo-wide search (all langs, excl. tests/dist) finds it
   only in `event-store/schemas.ts` (declaration), `telemetry/telemetry-projection.ts` (a fold
   into `view.turns` for the `output_tokens_high` hint), and tests. **Nothing appends it** — the
   `#1262` telemetry middleware emits `tool.invoke/completed/errored` to `TELEMETRY_STREAM`, never
   `turn.completed`. The schema header's *"Emitted by the telemetry middleware"* is aspirational.
2. **The real token data lives on a disjoint substrate the feature views can't see.** Per-turn /
   per-session token totals are `SessionTurnEvent`/`SessionSummaryEvent` records in
   `<stateDir>/sessions/<sessionId>.events.jsonl`, read lazily by `session-provenance-projection`.
   Keyed by `sessionId` (+ optional `workflowId`) — **no `teammateName`, no `taskId`, no
   `operationId`.** `team-performance-view` / `delegation-timeline-view` are strict single-stream
   left-folds over the **SQLite feature event stream** and never read this substrate.
3. **The teammate↔session join does not exist.** `team.teammate.dispatched` / `team.task.*` carry
   `teammateName`+`taskId` but **no `sessionId`**; the session manifest/JSONL carry
   `sessionId`/`workflowId`/`cwd`/`branch` but **no teammate identity**. Only latent bridge:
   `team.teammate.dispatched.worktreePath` ≈ manifest `cwd`.
4. **`operationId` (#1291) cannot bridge it.** The stamping is `AsyncLocalStorage`, single-process
   (`dispatch/dispatch-context.ts`); it cannot reach a subagent's turns (separate session/process),
   and turns aren't on the feature stream regardless.
5. **The only token source today is session-end transcript parsing.** `cli-commands/session-end.ts`
   → `parseTranscript` writes the JSONL/rollup **at session end**. So token data is (a) unavailable
   at `team.task.completed` time (task-completion precedes session-end), and (b) sourced by
   **transcript parse** — the exact mechanism the research forbids as a token source for C
   (*"never by re-parsing a transcript"*) and the coupling Option B was rejected for.

**Consequence:** A-pure (pure projection over an existing joinable atom) is dead. C-as-written
("correlate the per-turn atoms") is **not implementable** because no per-turn atom producer exists
on the feature stream — the per-turn token primitive must be *created first*. Whatever we build,
Half 1 requires a **new producer** that puts teammate-keyed token data on the feature stream — a
runtime/hook-layer seam (INV-4 surface), not the "projection-only" change the plan scoped.

**Decision: escalated to user** (premise invalidated → genuine fork). Candidate paths:
- **A-with-link (enrich completion):** teammate-side completion hook stamps its own output-token
  total onto `team.task.completed` (new optional `outputTokens`); views fold it keyed by
  `teammateName` — pure left-fold, no new event type, OTel-aligned (tokens as an attribute on the
  agent-step "span"). **Blocker:** token total isn't available until session-end, after completion.
- **C (new atom):** minimal `subagent.tokens_used {teammateName, taskId, outputTokens}` on the
  feature stream at the dispatch-completion boundary. **Blocker:** same timing; source would be the
  forbidden transcript parse unless a per-turn producer is added.
- **Defer Half 1 / re-scope #1525:** the honest precondition is a *per-turn token producer on the
  feature stream stamped with teammate identity* — a larger lift than W2 budgeted. Proceed with
  **Half 2 (mutation trend, W2-5..W2-7)** which has real atoms (`gate.executed`/`mutation.executed`)
  and is unaffected.

### Half-1 RESHAPE (2026-06-19, post-SubagentStop spike) — capture-seam build, not a projection add

The SubagentStop harness spike (claude-code-guide) settled the seam. Net: **the design §5.1 was
right all along** ("emit `subagent.tokens_used` at subagent-dispatch completion"); the discovery
research's Option A was a detour off the false "atom already emitted" premise. Reshaped Half-1
reverts to the design's emit, now concretely sited:

**SubagentStop facts (Claude Code):**
- The `SubagentStop` hook payload carries `agent_id`, `agent_type`, `agent_transcript_path`
  (the subagent's **own** transcript JSONL), `cwd` — but **NO token counts** (no hook exposes them).
- Subagents share the parent `session_id` and do **not** fire their own SessionStart/SessionEnd —
  so the session-provenance substrate never captures them. SubagentStop is their only lifecycle hook.
- The only token source is parsing the subagent's own transcript (`usage.output_tokens` per
  assistant message). Parsing the *subagent's own* transcript at *its* stop is the legitimate atom
  source — distinct from the forbidden parent-session-end re-parse of a commingled blob.

**Reshaped tasks (supersede the projection-only W2-2..W2-4 below):**
- **H1-A — SubagentStop hook handler.** New `exarchos subagent-stop` CLI command; wire `SubagentStop`
  in `hooks-src/hooks.json` (rendered per-runtime). Fail-open/observe-only (mirror session-start/end).
  Reads `agent_transcript_path`, sums `usage.output_tokens`, emits `subagent.tokens_used` to the
  feature stream. INV-4: Claude-Code-specific seam; other runtimes degrade to empty (fold-what-exists).
- **H1-B — teammate-identity correlation (the open design sub-decision).** Payload gives
  `agent_id`/`agent_type`/`cwd`, NOT `teammateName`/`taskId`. Bridge options: (i) `cwd ≈ worktreePath`
  → join `team.teammate.dispatched` (worktree-isolated teammates only); (ii) capture the parent Agent
  tool `tool_use_id ↔ agent_id` at dispatch. Resolve before H1-D.
- **H1-C — schema + registration.** `subagent.tokens_used { agentId, agentType, outputTokens, … }` +
  `EVENT_DATA_SCHEMAS` + emission registry (source: hook). This is the design's "the event *is* the
  record (INV-1)" — a correctly-sourced atom (C), not a re-recorded aggregate (B).
- **H1-D — projection fold.** Extend `team-performance` / `delegation-timeline` to fold
  `subagent.tokens_used` keyed by the H1-B correlation (the original W2-2/W2-3 intent, now over a
  **real** atom). **H1-E — surface via `exarchos_view`** (original W2-4).

**Scope verdict:** this is a real capture-seam build (new hook + schema + correlation + fold), larger
than preview.1's original projection budget. **[Shipped 2026-06-20]** it landed in preview.1 W2 after
all (H1-A..H1-E below); what remains deferred to a follow-up #1525 sub-slice is the **live
end-to-end population proof** (the hook registered in active settings + a worktree-isolated dispatch).
Half 2 ships preview.1 independently. The original W2-2..W2-4 below are retained for reference but
**superseded** by H1-A..H1-E.

## Half 2 — Mutation-score trend (same INV-1 principle, different atom)

### Task W2-5: GROUND the mutation atom + trend targets (investigation)
1. Confirm the shape of mutation score on `gate.executed` / `mutation.executed` (per-skill / per-module dimension), and the current `code-quality` / `eval-results` view fold structure. Record findings; adjust W2-6 test names to the real fields.

**W2-5 FINDING (2026-06-19) — Half 2's atom is real; this is a genuine clean fold (unlike Half 1):**
- **Score lives on `gate.executed.details.mutationScore`, NOT `mutation.executed`.** `mutation.executed`
  is the INV-10 liveness terminal — `{command, repoRoot, passed, exitCode}` only, no score.
  `mutation-adequacy.ts` (`orchestrate/`) parses the Stryker report, computes
  `mutationScore = killed / (total − noCoverage)`, and emits a **foldable `gate.executed`**
  (`mutation-adequacy.ts:531-561`) carrying `details.mutationScore` (number, 0..1). Per-skill
  dimension = `details.skill` (the existing `GateExecutedDetailsSchema` passthrough).
- **`code-quality-view` already folds `gate.executed` keyed by `details.skill`** (`handleGateExecuted`)
  and already has a trend primitive: `BenchmarkTrend { values:[{value,commit,timestamp}], trend }`
  + `calculateTrend` (last-3 slope). `SkillQualityMetrics` has no mutation field yet.
- **Semantics gotcha:** mutation score is **higher-is-better**, the inverse of `calculateTrend`'s
  benchmark-latency convention (it calls a *decreasing* series "improving"). W2-6 GREEN needs a
  direction-aware trend (e.g. `calculateTrend(values, { higherIsBetter: true })`).
- **W2-6 stays as written** (`CodeQuality_FoldsMutationScore_ExposesPerSkillTrend`): fold
  `gate.executed` where `details.mutationScore` is a number, append to a per-skill ordered-sample
  trend mirroring `BenchmarkTrend`. Pure left-fold, no side table (INV-1). Atom is real → no
  producer gap. **Half 2 is unblocked and proceeds now.**

**Dependencies:** None (parallel with Half 1). **Parallelizable:** Yes.

## Invariant conformance
- **INV-1:** both halves are left-folds over existing atoms; no side tables, no re-recorded aggregates (the whole point of choosing A over B).
- **INV-4:** token/mutation atoms are runtime-dependent; the views fold whatever exists and degrade to empty on runtimes that don't emit them — no new platform-coupled emission seam (A) beyond, at most, one correlation stamp.
- **INV-10:** mutation runs stay event-emitted + offline/sampled; never on the inner loop.
- **INV-5b:** new metrics ride the existing view output carriers / registered outputSchemas.
