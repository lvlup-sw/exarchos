exarchos · system design

Event-sourced by design,
cooperative by default

Exarchos is local agent governance: a single-machine, event-sourced process manager that lets several coding agents work the same repository at once without stepping on each other. This page reads from the outside in. First what it is built to optimize for, then how a workflow actually moves through the runtime, where state lives, how it stays correct when agents run in parallel, why governance scales with risk instead of applying to everything equally, how one runtime serves many agent harnesses without hand-rendering each, and where the roadmap is heading. Each section names the decision behind it: the force, the choice, and what was given up. A reference tail at the end is there to look things up in.

00 · the forces

What this system is built to optimize for

Agents made code generation cheap. The cost did not vanish, it dispersed across the value chain to the two ends a person still bounds: planning and context upstream, where the work gets aimed, and review and verification downstream, where nothing ships until it is checked. Exarchos is a workflow engine that complements the coding agent, not another harness. It earns its keep at those two ends. It makes planning and verification depth proportional to the risk of the change rather than charging every task the same ceremony, and it keeps several agents correct on one repository by routing every mutation through one append-only log. The aim is governed throughput sized to risk: as much planning and verification as the change warrants, and no more.

Goals

  • Governed throughput without a ceremony tax: verification and planning depth proportional to the risk of the change.
  • Durable, replayable workflow state: reconstruct what happened and why, from the log alone.
  • Cooperative concurrency: many agents on one repository, serialized by the substrate, not by manual coordination.
  • One contract, one core: the MCP contract is the single invocation surface, and the CLI is a presentation client over it, equal by construction.
  • Recovery that never loses work: native undo first, refuse-to-discard second, destructive overwrite never.

Non-goals

  • Not a distributed system. One machine, cooperative agents. No saga, no two-phase commit, no leader election.
  • Not a daemon or a background supervisor. Liveness is observed from events, queried on demand.
  • Not a model harness. Exarchos governs the workflow; the coding agent stays whatever the operator runs.
  • Not uniform process. Mandatory red-green-refactor on every task is the thing being replaced.
  • Not a render-everything-per-harness shim. Where an open standard converged we conform to it; bespoke rendering is reserved for what no standard covers.
01 · the pieces

How a workflow moves

A request enters once and travels down a fixed stack. An agent or the CLI calls a verb. The dispatch core resolves it the same way for both surfaces. Anything that changes state appends an event; nothing is written in place. Projections fold those events into the read models that answer the next question, and the state machine for the workflow type decides which transitions are legal. The response carries next_actions: the moves now available, which the agent reads and dispatches. It never polls.

The same nine layers, named, from storage up to the agents that consume the surface:

L1StorageSQLite in WAL mode: the events, the projected state, the streams, the idempotency claims.sqlite-backend.ts
L2Event storeAppend with optional expected-sequence and idempotency key. A composite primary key makes a duplicate sequence impossible.atomic-appender.ts
L3ProjectionsPure reducers, registry-bound, snapshot-cached. Reconcile rebuilds any read model from the first event.projections/
L4Workflow primitivesThe per-type state machine, the capability resolver, the phase contracts, the pruner. Only one action mutates a phase.topology/ · workflow/
L5Dispatch coreA single function over a context that carries storage, the event store, the resolver, and telemetry.core/dispatch.ts
L6Composite toolsFour visible tools, each with an action discriminator, a registered output schema, and per-action annotations.orchestrate/ · views/
L7Lifecycle verbsps, describe, wait, export: generic windows over the log, shipping with v2.12. No per-feature lifecycle code.cli-commands/
L8AdaptersCLI and MCP over one dispatch core. The MCP contract is the invocation surface and the CLI a client over it: asserted equal by a parity harness today, generated from the tool schemas next (§05).adapters/
L9Cooperative agentsClaude Code, Codex, Cursor, OpenCode and others. Each declares a posture and reads next_actions instead of polling; the runtime meets them through converged standards plus thin on-ramps, not a bespoke render per harness (§05).runtime

Two rows are highlighted (L2 event store, L5 dispatch core): the load-bearing spine the rest of the stack leans on. One row is dashed (L7 lifecycle verbs): in flight for v2.12, not yet landed.

Decision: the log is the authority, read models are a cache enforces INV-1
Forces
Workflow state is touched from many places: a phase transition, a task completing, a merge recovering. If each writer edits a shared record, two writers race and the record drifts from what actually happened.
Choice
Every mutation is an appended event. State is a deterministic fold over the event stream. A snapshot accelerates a cold start, and reconcile rebuilds from event zero when a snapshot is stale or absent.
Rejected
A mutable system of record with the event log as an audit sidecar. Familiar, but it makes the cache the truth and the log a story nobody trusts.
Cost
Read models must be pure and replay-safe, and a projection that throws has to degrade to a rebuild rather than serve a wrong answer.
02 · state

Where state lives, and the file we retired

State lives in one place: the event log, projected into a SQLite workflow_state table the runtime folds from events. Whether a workflow exists is an event-store question, answered by _meta.workflowExists, never by a file on disk. An earlier <featureId>.state.json planner file was retired in #1504: production no longer reads or writes it, and the path string survives only as a legacy identifier. The rule that outlived the file is the one worth keeping: filesystem presence is never an existence signal.

Decision: retire the state file, keep one surface #1504 · INV-1
Forces
A second on-disk surface, the planner's stamp, could drift from the log and tempt callers to read it as truth or to stat its presence as an existence check. That presence check was the source of a real integrity incident.
Choice
Retire the .state.json write path (#1504). State is the SQLite workflow_state projection folded from events; existence is the _meta.workflowExists field from rehydrate or get.
Rejected
Keeping the file as a convenience cache. A second source of truth is a second thing to corrupt, and its presence invites the exact filesystem-existence check that broke.
Cost
A vestigial stateFile path string lingers as a legacy identifier. Callers route through the projection, never stat a path.
03 · under concurrency

Staying correct when agents run in parallel

Several agents writing the same repository is the normal case, not the exception. Correctness comes from serializing writes to a stream in two tiers, with no process lock and no advisory file. Inside one process, a per-stream promise chain runs same-stream appends one at a time. Across processes, SQLite's write-ahead log takes the write lock up front, and a per-stream version gate assigns and checks the next sequence atomically inside that transaction — the convergent event-store primitive (Marten, SQLStreamStore, EventStoreDB). Because the gate runs under the held write lock, a plain append never races: the second writer simply serializes behind the first and is handed the next sequence. Only a genuine optimistic-concurrency mismatch — a caller that passed a stale expected version — surfaces a conflict, carrying its expected and actual values directly; the composite primary key is retained as an integrity backstop, not the detector. That is the whole concurrency story, and it is deliberately not a distributed one.

Decision: a single-machine frame, held on purpose enforces INV-15
Forces
Concurrent agents look like a distributed-systems problem, and the textbook answers (saga, two-phase commit, leader election, vector clocks) are right there to reach for.
Choice
Treat it as what it is: one machine, one event store, cooperative agents. Serialize with the write-ahead log and optimistic retry. Compensation is a local rewind over the log, never a command sent to a remote participant.
Rejected
Saga orchestration, distributed locks, a supervisor process. They solve partition and multi-owner problems that do not exist here, and they import scaffolding that misleads every future reader.
Cost
The frame is a boundary, and a candidate design that needs one of those primitives is a signal the boundary is being crossed, not that the primitive is due.
04 · the first thesis

Why depth scales with risk

This is the idea the rest of the roadmap turns on. Two kinds of effort used to apply uniformly to every task: how hard you verify, and how much you plan. Exarchos makes both proportional to the change. A riskTier stamped on a task picks its verification ladder, from a bare typecheck at the low end to a full suite with a mutation-adequacy backstop at a boundary. A designDepth does the same for planning, scaling a single artifact from a terse plan to a full design-and-decompose. Both resolve once, when the phase is entered, and then freeze for the life of the task. They are the same move on one resolver, one applied to verification and one to planning.

The verification ladder, by tier
tierwhat it earnscost
lowtypecheck plus lint; structural checks onlyseconds, no tokens
mediumscoped tests plus an outcome-based adequacy probea focused run
high / boundaryfull suite, integration checks, mutation-adequacy backstopwall-clock, run offline
Decision: replace mandatory red-green-refactor with a risk-proportional ladder issue #1515
Forces
The most expensive part of strict test-first, the failing-test-first ordering and the history gate that enforces it, has the least evidence behind it. The benefit lives in the cheap part: an executable check and real feedback. Charging full ceremony per task taxes the work that needs it least.
Choice
Stamp a riskTier and a boundary flag per task; resolve the gate set from them. Keep the outcome-based adequacy check, drop the ordering mandate. Relaxing test-first is only safe with a backstop, so mutation testing guards the boundary, where its wall-clock cost belongs.
Rejected
Uniform red-green-refactor on every task. Defensible as a slogan, costly as a default, and weakly supported by the research it claims.
Cost
Tiering has to be wired through dispatch so the resolved tier actually reaches the prompt, and the resolver context now carries more than one depth field, which has to evolve as one schema.
05 · the second thesis

How one runtime serves many harnesses

A second thesis runs alongside the first. Exarchos serves several agent harnesses at once, and the naive way to do that, rendering every concern once per harness and then guarding the renders against drift, taxes the system with every new runtime while still proving the wrong thing: a guard proves the artifacts match, never that the guarantee holds. The move is to split by whether an open standard exists. Where one converged, conform to it and ship a single artifact. Where none did, stop rendering and enforce the invariant at a chokepoint every harness must cross.

Decision: conform where a standard converged, enforce where none did reframes INV-2 · INV-4 · INV-11 · #1601
Forces
Six runtimes, several concerns apiece: skills, instructions, hooks, subagents, worktree isolation. Rendering each concern per harness and then guarding the renders against drift is a tax that grows with every new runtime, and the guards see only the bytes. They prove the artifacts match, not that the guarantee holds: worktree isolation is enforced by construction on one runtime and merely advised on the others.
Choice
Split by whether a standard exists. Where one converged — Agent Skills, AGENTS.md, MCP — emit one standard artifact and let the harness read it; a bare logical tool name carries the only per-harness variance. Where none did — hooks, subagents, worktree isolation — enforce at a chokepoint every harness must cross: state in the dispatch and MCP handler, space in a spawn-bounded launcher that owns the worktree. The generator shrinks to the thin on-ramps that route each harness in.
Rejected
A bespoke render per harness per concern, kept honest by ever more structural guards. It scales the tax with every runtime and never closes the enforcement gap the guards cannot see.
Cost
The launcher owns process spawn, held to the single-machine frame: set up, exec, tear down, no daemon. The CLI becomes a client of the MCP contract rather than a peer facade. INV-11's by-construction promise became true everywhere once the launcher landed (v2.12.0-preview.1); it now owns spawn-time orientation injection (fail-open) and is the lifecycle authority whose launch.* events answer ps/wait liveness without a process scan.
06 · where it's going

Three zones, converging on one IR

The open roadmap is not a list of features. It is three zones layered on the same primitives, each a step toward folding the runtime into a single authored intermediate representation. Read top to bottom, they are: make depth adaptive, make the running system observable, then consolidate both into a builder that emits the IR. The discipline that keeps it honest is simple. Every interim change names how it lowers into that IR, or it is churn the consolidation will undo.

Z1v2.11 · adaptive depth
One resolver, two depths. Verification depth (riskTier, #1515) and planning depth (designDepth, #1581) plus the ship-gate obligations (#1592) all extend a single phase-kind resolver. They evolve as one schema, reviewed together.
Z2v2.12 · runtime supervision
One liveness convention. The lifecycle verbs (#1090) own the subscription and liveness convention; the worktree lifecycle manager (#1574) and the Marten consumers (#1342) emit and read events that conform to it. No parallel liveness model.
Z3v3.0 · consolidation
One way to define a workflow. The Workflow Builder SDK (#1258) compiles a fluent definition to a typed IR and deletes the closed-form registries. Every Z1 and Z2 edit must lower into a combinator or defer until the migration consumes it.
v2.11.0nowVerification & Reliability: the adaptive-depth zone: the verification ladder, the design-and-plan collapse, the ship-gate obligations, the onboarding reconciler.
v2.12.0nowProcess Lifecycle Verbs: ps, describe, wait, export over the log, plus the worktree lifecycle manager and the remaining event-store consumers.
v3.0.0nextWorkflow Builder SDK: the consolidation endpoint: a fluent definition compiles to the IR; the hand-written state-machine registries are retired.
v3.1.0laterEval & Benchmark Suite: the two-tier eval redesign and the benchmark runs — measuring whether the shipped ladder earns its keep.
v3.2.0laterDesign Knowledge Graph: rationale as typed claims — asserted through events, folded into a queryable corpus, served as composed content over MCP. Documents become queries; coordination stays remote — basileus claims work, Exarchos workflows run independently.

The harness-agnosticism program (#1601) threads both live zones — the launcher and the hooks-into-dispatch move in Z2, the facade-as-MCP-contract codegen in Z3 atop the 2026-07-28 MCP migration (#1604). The design-knowledge-graph program (#1745, v3.2.0) extends the log's authority to design rationale itself: what the system believes becomes as replayable as what it did — claims asserted through the operations that produce them, a corpus that is a projection with no authority, and specs that are compositions rather than files. Milestones are themed to the convergence zones, not feature buckets. The full index, the coordination rules, and the open questions live in issue #1599.

The invariants

Everything above is the narrative. What follows is the reference, built to be scanned while you work. These are the architectural invariants the runtime holds, audited at review and enforced where they can be machine-checked. Full prose lives in .exarchos/invariants.md.

INV-1The append-only log is the source of truth; every read model is a pure fold over events.
INV-2CLI and MCP are interchangeable facades over one dispatch core; a parity harness proves it.
INV-3No decision presumes the transport is local; capability resolution stays handshake-authoritative.
INV-4Skills and workflows are not coupled to one harness; six runtimes are first-class.
INV-5aTool inputs are constrained at the schema level; every tool says when not to use it.
INV-5bEvery result carries a fixed shape; errors carry the fields an agent needs to self-correct.
INV-5cVerbs are queryable and dry-run-capable, borrowed from Aspire: agents query, they don't drive scripts.
INV-5dFour visible composite tools, each with an action discriminator and per-action annotations.
INV-6The runtime makes no assumption about which workflow type is running; specifics live in topology.
INV-7Concurrency serializes in two tiers: an in-process chain and the write-ahead log. No PID lock.
INV-8Every append carries an idempotency key; a unique index collapses duplicates at storage.
INV-9Every workflow type ships a state machine; only one action mutates a phase.
INV-10Long-running work emits a start event and a terminal event; lifecycle verbs query them generically.
INV-11Every agent declares a posture; a task-isolated agent cannot write outside its worktree, by construction.
INV-12next_actions publishes the affordances an agent perceives; agents dispatch them, they don't poll.
INV-13A non-idempotent effect emits intent before and result after, so a crash is recoverable.
INV-14Recovery prefers a native undo, then a refuse-to-discard reset, and never a destructive overwrite.
INV-15One machine, cooperative agents. No saga, no distributed locks, no leader election.

INV-2, INV-4 and INV-11 are being reframed by the harness-agnosticism program (#1601): the CLI becomes a client of the MCP contract (equivalence by construction), runtimes are served by standards-conformance plus a thin shim, and worktree isolation becomes launcher-enforced across harnesses. The catalog edit is tracked in #1608; the decision is §05.

colophon · about this document

Why this document is shaped the way it is

This page is itself a design decision, so it follows the same force, choice, and cost it asks of every section. It has to be one artifact that reads as an explanation, works as a map, and serves as a lookup tool.

Decision: a decision-spine narrative, not a spec dump sibling of basileus#182
Forces
A canonical reference is pulled three ways. An exhaustive section-by-section spec is complete but goes unread. A pure case study is compelling but hard to look things up in.
Choice
An outside-in narrative with an ADR-shaped decision in every section, a consistent visual legend, a forces-and-non-goals opener, and a reference tail kept visually distinct. Narrative to understand, tables to work.
Rejected
A strict twelve-section layout that reads as a checklist. Two separate documents, one to explain and one to look up, when the brief was for a single stop.
Cost
A new section has to earn a decision and a diagram, or it belongs in the reference tail as a table. That rule is what keeps the page canonical.

Companion to the basileus system-design page; same family language, exarchos hue. If you add a section, give it a decision: the force it answers, the choice, and what that choice gave up.
